# Sprint 02 — Knowledge / RAG Foundation

## Objective

Build the reusable knowledge-retrieval (RAG) abstraction future RAG-enabled agents will use,
per CLAUDE.md §4.4 ("RAG is documentary only... must provide source references and must not
replace Tools for live business data"), and integrate it into at least one existing agent
without rewriting that agent's business workflow.

## Scope

- Typed Knowledge/RAG framework (`src/rag/`): `KnowledgeProvider` Protocol, `KnowledgeRetriever`,
  `KnowledgeQuery`, `KnowledgeChunk`, `KnowledgeResult`, `KnowledgeMetadata`, typed exceptions.
- Deterministic `LocalKnowledgeProvider` (keyword/text scoring) over a small set of synthetic
  Markdown knowledge documents (`configs/knowledge_base/`) — no embeddings, no vector database.
- Integration into `ClaimsAgent` via dependency injection: retrieved knowledge feeds the
  existing `PromptManager`/`LLMProvider` flow as documentary context only, never a business
  fact, and never touches `ClaimsIntakeState`.
- `AzureAISearchProvider`: a second, production-shaped `KnowledgeProvider` implementation
  (PBI-02-02), configuration-selected, local remains the default for dev/tests. Reusable Bicep
  module provisioning the Azure AI Search *service* only (no index, no ingestion, no
  deployment performed).
- Grounding & Citations Framework (PBI-02-03): a reusable `Grounder` (`src/rag/grounder.py`)
  and typed contracts (`src/rag/grounding_models.py`: `Citation`, `CitationReference`,
  `GroundedContext`, `GroundedResponse`, `GroundingMetadata`) that turn retrieved
  `KnowledgeChunk`s into deduplicated, deterministically ordered, top-k typed citations —
  provider-agnostic (works with both `LocalKnowledgeProvider` and `AzureAISearchProvider`).
  `POST /chat`'s response gains additive, optional `citations`/`groundingMetadata` fields.
- Controlled LLM-driven Tool Calling (PBI-02-04): a reusable `ToolCallingOrchestrator`
  (`src/core/tool_calling/`, the first occupant of CLAUDE.md §6's reserved `src/core/`
  package) that exposes an Agent's allow-listed Tools to an `LLMProvider`, validates and
  executes any Tool calls it requests via the existing `ToolExecutor`/`ToolRegistry`
  (never recreated), and loops up to a conservative, configurable `max_iterations`. Typed
  contracts split across the LLM protocol boundary (`src/llm/models.py`:
  `LLMToolDefinition`, `ToolCallRequest`, `ToolCallArgument`) and the orchestration boundary
  (`src/core/tool_calling/models.py`: `ToolCallResult`, `ToolCallingContext`,
  `ToolCallingResponse`, `ToolCallingError`). Per-Agent allow-lists for all three Agents
  (`src/core/tool_calling/policies.py`); only `ClaimsAgent` is actually wired to a live
  orchestrator this PBI. `MockLLMProvider` gained deterministic, opt-in scripted tool-calling
  for tests; `AzureOpenAIProvider` maps the same contracts to the OpenAI function-calling API,
  fully mocked in tests. `POST /chat`'s response gains an additive, optional `toolCalls` field.

## Out of scope

- Embeddings, vector databases, semantic ranking (not justified for this synthetic corpus).
- Real company/customer documents.
- RAG evaluation/quality metrics.
- RAG index creation and document ingestion pipelines.
- APIM, authentication, Azure deployment.
- Integrating Knowledge retrieval into Broker or Commercial Intake (deferred — only one agent
  was required this PBI; see `decisions.md`).
- UI rendering of citations (PBI-02-03 is backend-only).
- Autonomous unrestricted agents, dynamic plugin loading, code execution / shell / browser
  Tools, and wiring `ToolCallingOrchestrator` into Broker or Commercial Intake (PBI-02-04;
  their allow-lists are defined and tested, not yet integrated — see `decisions.md`).

PBI-02-04: Controlled LLM-driven Tool Calling built as a new `src/core/tool_calling/` package — the first real occupant of CLAUDE.md §6's reserved `src/core/` ("orchestration... permissions"). Typed contracts split across two boundaries: `src/llm/models.py` owns the LLM-protocol-facing shapes (`LLMToolDefinition`, `ToolCallRequest`, `ToolCallArgument`; `LLMMessageRole` gained `TOOL`, `LLMMessage` gained `tool_call_id`, `LLMRequest`/`LLMResponse` gained additive `tools`/`tool_calls` fields), since `src/llm/` must never depend on `src/core/` (orchestration sits above, not below, the framework layer); `src/core/tool_calling/models.py` owns the orchestration-facing shapes (`ToolCallResult` — API-facing, camelCase, mirroring `Citation`'s own precedent — `ToolCallingContext`, `ToolCallingResponse`) plus `exceptions.py` (`ToolCallingError`, reserved for genuine misconfiguration only) and `policies.py` (per-Agent allow-list constants for all three Agents, though only Claims is wired this PBI). `ToolCallingOrchestrator` reuses `ToolRegistry`/`ToolExecutor` exactly as-is — constructor-injected, never recreated — and adds the one authorization boundary neither of those has: an LLM-requested tool is checked for existence in `ToolRegistry` (else `error_type="unknown_tool"`) and then membership in the calling Agent's `ToolCallingContext.allowed_tools` (else `error_type="unauthorized"`) *before* `ToolExecutor` is ever invoked; any resulting `ToolExecutor` failure (malformed arguments, execution exception) is reported as `error_type="tool_failed"`, exactly mirroring `ToolExecutor`'s own "never raise to the caller" contract.
