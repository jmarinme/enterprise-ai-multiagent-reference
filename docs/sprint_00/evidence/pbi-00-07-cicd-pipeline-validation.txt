--- Stage 1 (Backend Quality) command-by-command validation ---
Environment: root .venv (Python 3.11.9 — pre-existing gap vs. required 3.12, see prior PBIs'
decisions.md entries; the pipeline itself pins UsePythonVersion to 3.12, so CI will actually run
on the correct version even though local validation could not).

Combined dependency install (apps/api's pyproject.toml deps+dev extra, plus root pyproject.toml's
deps+dev+cosmos+keyvault extras, plus pytest-cov) installed successfully into one shared venv,
proving the "one shared environment" CI design actually works (previous PBIs used two separate
local venvs and never verified this combined-install path before).

Command: pytest tests/unit/api tests/unit/domain tests/unit/services tests/integration -v
  --junitxml=... --cov=src --cov=apps/api/src --cov-report=xml:... --cov-report=term
Result: 26 passed, 2 skipped (both live-integration scaffolds skip correctly), coverage XML
generated, overall coverage 75% (100% on most modules; the Cosmos and conversation-store-factory
modules read 0% because their integration test is skipped without Azure config, as designed).

Command: ruff check apps/api/src src tests
Result: FAILED on first run — 3x I001 (unsorted imports) in tests/unit/api/test_correlation_id.py,
test_health.py, test_version.py. Root cause: these three files were never actually ruff-checked
before this PBI. PBI-00-02 only ran `ruff check .` from inside apps/api (covering apps/api/src
only); tests/unit/api/ lives outside that directory and was never included in any prior ruff
invocation. This pipeline's combined, repo-root invocation is the first to cover it. Fixed via
`ruff check --fix`; re-ran pytest afterward to confirm the import reorder didn't affect test
behavior (still 5/5 in tests/unit/api). Final: All checks passed!

Command: mypy apps/api/src
Result: Success: no issues found in 11 source files.
Command: mypy src
Result: Success: no issues found in 16 source files.

this stage is expected to run successfully in actual Azure DevOps execution.

--- Conclusion ---
All 5 active stages' embedded commands were validated directly and pass. The pipeline requires
zero pre-existing Azure DevOps configuration (no variable group, no service connection) to run.
The disabled Deploy_Dev stage documents the exact future 6-step CD flow without executing any of
it (condition: false). Two real, pre-existing gaps were discovered and fixed by this PBI's more
thorough combined validation: an import-order lint gap in tests/unit/api/ (present since
PBI-00-02, never previously checked) and confirmation that the "single shared CI environment"
dependency-install design actually works end-to-end.
