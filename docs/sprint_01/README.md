# Sprint 01 — Core Multi-Agent Platform

## Objective

Build the core multi-agent orchestration platform: the Conversation API, context management,
the Supervisor orchestration framework, intent classification, registry-driven agent routing,
guardrails, and a human-escalation foundation — per `CLAUDE.md` §14's Sprint 01 scope.

## Scope

- Supervisor orchestration framework (interfaces, registry-driven routing, no concrete-agent
  coupling).
- Rule-based intent resolution (no LLM yet).
- Mock domain agents validating the registry pattern (Claims, Broker, Commercial Intake).
- `POST /chat` conversational entry point.
- Conversation persistence through the existing `ConversationRepository` (PBI-00-05).
- Further Sprint 01 PBIs (real agent business logic, LLM-backed intent classification,
  guardrails, human escalation, Tool registry/contracts) will be defined and added to the
  Deliverables list below as they are scoped — only PBI-01-01 is defined at Sprint start.

## Out of scope

- Azure OpenAI / Semantic Kernel / AutoGen / LangGraph / CrewAI.
- Prompt engineering, RAG, Azure AI Search, vector databases.
- Real Tool Calling against business systems.
- Authentication (Entra ID end-user login).
- Real insurance business logic in any agent.

## Deliverables

- [x] PBI-01-01: Build the Supervisor Agent orchestration framework.
- [x] PBI-01-02: Build the reusable Agent Tool Framework.
- [x] PBI-01-03: Build the reusable Prompt Management Framework.
- [x] PBI-01-04: Build the reusable LLM Adapter Framework with Mock and Azure OpenAI providers.
- [x] PBI-01-05: Build the first functional Claims Agent (claim-notice intake flow).
- [x] PBI-01-06: Build the functional Broker Agent (broker-services support flow).

PBI-01-05: `ClaimsAgent` converted from a framework/mock demo agent into a real, functional, multi-turn claims-intake business agent (`src/agents/claims_agent.py`, plus a new `src/agents/claims/` subpackage: `state.py`, `extraction.py`, `workflow.py`). A dict-dispatched state machine (`NEW → COLLECTING_INFORMATION → VALIDATING_POLICY → READY_TO_REGISTER → REGISTERED → ADJUSTER_ASSIGNED`, no if/elif chain) gathers 9 required fields one at a time via fully deterministic regex/keyword extraction (`MockLLMProvider` cannot perform real NLU, so no business fact may depend on it), validates the policy and payment status, registers a synthetic claim, and assigns a synthetic adjuster. Only "policy not found" blocks progression — an inactive policy or a payment issue is surfaced as a fact, never a gate, which is the only way to satisfy both "determine active/paid status" and "must not approve or deny a claim." Three new Tools (`PaymentStatusTool`, `ClaimRegistrationTool`, `AdjusterAssignmentTool`) added under `src/services/tools/`, all called only through `ToolExecutor`; `PolicyLookupTool` reused, with `SYNTHETIC_POLICIES` additively extended with the 4 required scenarios (`SYN-POL-0001` active+paid, `SYN-POL-0002` active+payment-issue, `SYN-POL-0003` inactive, any unrecognized number = not found). Per-turn working state round-trips through `Conversation.metadata`/`ConversationContext.metadata`/`AgentResponse.metadata` (new, additive plumbing through `src/supervisor/models.py`, `context.py`, `orchestrator.py`, and `ConversationRepository.append_message`'s new optional `metadata` parameter) — legitimate session state, not core business truth, since the authoritative record is what `ClaimRegistrationTool` simulates. The user-facing response text is always deterministic (Tool/state-machine derived); `PromptManager` and `LLMProvider` are still genuinely invoked every turn (provable via `[prompt=...]`/`[llm=...]` response annotations) so the same `ClaimsAgent` code works unmodified against a real `AzureOpenAIProvider`, but the LLM is never the source of a business fact. `configs/prompts/claims/system.md` rewritten (version bumped 1.0.0 → 2.0.0) with the PBI's explicit tone/scope requirements; `POST /chat`'s `ChatResponse` gained an additive, generic `metadata` field (no claims-specific typing, keeping the route free of business logic). A real, blocking bug was found and fixed during validation: `SupervisorOrchestrator` re-resolved intent from every individual message via keyword matching, so an ambiguous follow-up (a bare policy number, a plain "yes"/"no") had no CLAIMS keywords and was misrouted to `FallbackAgent` mid-conversation — fixed with one uniform, agent-agnostic fallback rule (stay with the conversation's current agent when the new message doesn't match any known intent), not per-agent-type branching; see decisions.md. 182/182 tests pass deterministically with no Azure dependency (full Supervisor/Tool/Prompt/LLM/`/chat` regression suite confirmed passing, including the 4 pre-existing Claims Agent dependency-injection tests updated to reflect this PBI's intentional behavior change); ruff and mypy clean; live smoke test confirmed a complete 10-turn claim report (report → policy/payment/date/location/loss-type/description/name/phone/injuries/third-parties → registration → adjuster assignment) through the real running API, plus confirmed fallback routing is unaffected for genuinely new/unrelated conversations. No real claims system, real adjuster assignment, real customer data, RAG, Azure AI Search, APIM, authentication, document upload/OCR, coverage adjudication, fraud detection, payments, claims settlement, or additional agent framework implemented. — 2026-08-07
Evidence: `docs/sprint_01/evidence/pbi-01-05-claims-agent-validation.txt`

PBI-01-06: `BrokerAgent` converted from a static mock into a real, functional, multi-turn broker-services agent (`src/agents/broker_agent.py`, plus a new `src/agents/broker/` subpackage: `state.py`, `extraction.py`, `workflow.py`), structurally mirroring `ClaimsAgent`'s shape (PBI-01-05) rather than sharing a base class with it — see decisions.md for the explicit "only two data points" reuse-inspection verdict. A dict-dispatched state machine (`NEW → IDENTIFYING_REQUEST → COLLECTING_INFORMATION → LOOKING_UP_DATA → READY_TO_RESPOND → [READY_TO_REQUEST_PAYMENT → PAYMENT_REQUEST_REGISTERED] → COMPLETED`, no if/elif chain) deterministically classifies the inquiry (policy status / transaction status / commission, keyword-based) and gathers only that inquiry type's required fields — one combined prompt when more than one field is missing (`"Please provide your broker ID and the period you want to review."`, matching the PBI's own example verbatim), one field's own prompt otherwise. Reuses `PolicyLookupTool`, `PaymentStatusTool`, and `BrokerAccountLookupTool` unmodified for policy/payment/broker verification — deliberately did **not** create the PBI-suggested `PolicyStatusTool`/`PolicyPaymentStatusTool`, since that would duplicate capability those existing Tools already provide. Three genuinely new Tools added (`TransactionStatusTool`, `CommissionLookupTool`, `CommissionPaymentRequestTool`, the last mirroring `ClaimRegistrationTool`'s stateless sequential-reference shape), plus additive synthetic data (`SYN-BRK-0001/0002`, `SYN-TXN-0001/0002`, commission records keyed by `(broker_id, period)` covering available/paid/pending). A commission-payment request is only offered when the commission is `"available"`; re-messaging after one is registered reports the existing reference rather than submitting a duplicate, mirroring `ClaimsAgent`'s adjuster-assignment duplicate-prevention precedent exactly. Live end-to-end validation against the real API surfaced two real bugs, both fixed: (1) `RuleBasedIntentResolver`'s `_BROKER_KEYWORDS` did not match the PBI's own literal example phrasing ("status of a policy" vs. the resolver's exact-substring "policy status"), so that message never reached `BrokerAgent` at all — fixed by adding bare `"policy"`/`"transaction"` keywords; (2) `_handle_ready_to_respond`'s same-turn fall-through into `_handle_completed` produced a redundant, duplicated fact statement — fixed by ending the turn immediately after the lookup's own notice (`should_continue=False`) rather than continuing into a same-turn summary. Both are documented in decisions.md with regression tests (`tests/unit/supervisor/test_intent.py`, `tests/unit/agents/broker/test_broker_workflow.py`). No changes were needed to `src/supervisor/orchestrator.py`, `ConversationRepository`, or `POST /chat`'s contract — the PBI-01-05 metadata round-trip and ambiguous-follow-up routing-continuity fallback were reused with zero modification, proving those PBI-01-05 mechanisms are genuinely agent-agnostic. 237/237 tests pass deterministically with no Azure dependency (full Supervisor/Tool/Prompt/LLM/Claims/`/chat` regression suite confirmed passing); ruff and mypy clean; live smoke test confirmed all three inquiry types plus a full commission-to-payment-request flow through the real running API. No real broker/policy/commission system, real customer data, real financial transaction, RAG, Azure AI Search, APIM, or authentication implemented. — 2026-08-07
