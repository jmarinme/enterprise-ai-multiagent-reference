--- Live smoke test ---
Started the API via `uvicorn main:app --app-dir apps/api/src` and issued a real POST /chat
request routed to the (now Tool-injected) ClaimsAgent:
  POST /chat {"message":"I need to check my claim","userId":"demo-user"}
  -> 200 {"conversationId":"...","agent":"ClaimsAgent","intent":"CLAIMS",
          "response":"... (synthetic claim lookup: status=under_review)"}
This confirms the full chain end-to-end through the real composed API: Agent -> ToolExecutor ->
ToolRegistry -> ClaimsStatusTool -> typed input validation -> execution -> typed ToolResult ->
Agent -> Supervisor -> Conversation Store -> JSON response. Server stopped after verification.

--- Conclusion ---
The Tool framework is implemented as a clean, interface-only pipeline mirroring the Supervisor
framework's proven shape: ToolExecutor never contains business logic, ToolRegistry has no
hardcoded routing and fails explicitly on duplicate registration or missing tools, and every
public contract (ToolRequest, ToolResult, ToolMetadata, ToolExecutionContext) is a typed
Pydantic model with exactly one deliberately-justified untyped boundary
(ToolRequest.tool_input). ClaimsAgent now demonstrates real ToolExecutor injection without the
Supervisor knowing anything about Tools. All 82 tests pass deterministically with no Azure
dependency; ruff and mypy are clean; a live smoke test proves the full pipeline works through
the real running API. No Azure OpenAI, RAG, APIM, real integrations, or real business data was
implemented.
