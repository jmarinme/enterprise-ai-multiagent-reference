--- Docker build-context fix (prerequisite, not scope creep) ---
Problem found during architecture inspection: apps/api/src/main.py needs to import
src.supervisor.*/src.agents.*/src.domain.* for POST /chat, but the existing Dockerfile/compose
build context (./apps/api) has no visibility into the top-level src/ package at all — the
Docker image would have built (nothing referenced src.* yet before this PBI) but would break
at runtime the moment chat.py's import chain executed inside a container.

Fix: docker-compose.yml's api service build context changed to the repo root (`.`) with
`dockerfile: apps/api/Dockerfile`. The Dockerfile now COPYs apps/api/src to /app/app_src
(importable as bare main/api/config/observability via --app-dir, unchanged behavior) and the
repo-root src/ to /app/src (importable as `src.*` via ENV PYTHONPATH=/app). No naming collision:
one tree is imported bare, the other under the `src.` prefix — this mirrors how tests/unit/api's
conftest.py (bare apps/api/src insertion) and the root pyproject.toml's pythonpath=["."]
(src.* insertion) already coexist for local test runs. apps/api/.dockerignore was removed
(Docker only reads .dockerignore from the build-context root, which is no longer apps/api/) and
replaced with a root .dockerignore.

Validated via: `docker compose config` (see below) — could not validate `docker build` itself,
Docker daemon unavailable locally (see "Container build" section).

--- Live smoke test ---
Started the API via `uvicorn main:app --app-dir apps/api/src` (same invocation style used in
every prior PBI's smoke test) and issued two real HTTP POST /chat requests:
  POST /chat {"message":"I need to report a claim","userId":"demo-user"}
    -> 200 {"conversationId":"...","agent":"ClaimsAgent","intent":"CLAIMS","response":"..."}
  POST /chat {"message":"random unrelated text","userId":"demo-user"}
    -> 200 {"conversationId":"...","agent":"FallbackAgent","intent":"UNKNOWN","response":"..."}
This directly demonstrates the full success-criteria pipeline: POST /chat -> Supervisor ->
Intent Resolver -> Registry -> Mock Agent -> Conversation Store -> JSON Response. Server stopped
after verification.

--- Conclusion ---
The Supervisor orchestration framework is implemented as a clean, interface-only pipeline:
the Supervisor (orchestrator.py) never imports a concrete agent, agent selection is a single
dict lookup inside the registry (no if/else/switch), and adding a new agent requires only a
new class + one registry.register() call in the composition root (apps/api/src/api/dependencies.py)
— zero changes to the framework itself. All 60 new+existing unit tests pass deterministically
with no Azure dependency; ruff and mypy are clean on both trees. The prerequisite Docker
build-context fix keeps the API image's shape correct for the new cross-package dependency,
though the actual `docker build` remains unverified locally (daemon unavailable). No Azure
OpenAI, RAG, APIM, or business logic was implemented.
