# Multi-Agent Observability (PBI-13-01)

## 1. Purpose and scope

A separate, authenticated-only experience (`/observability`) that shows *what happened* in
business/agentic terms for each conversation and processing run — intent, routing, tool usage,
tokens, estimated cost, latency — without redesigning the existing chat experience. This is
**Phase 1** (core: correlation, persistence, summary/list/detail APIs, basic dashboard). Phase
2 (deterministic quality signals, Operational Quality Score) and Phase 3 (advanced filters/UX)
are deferred — see §12.

## 2. Business vs technical observability

These are deliberately kept separate (PBI-13-01 §2):

| | Business/Agentic Observability | Technical Observability |
|---|---|---|
| Answers | What did the user ask, which agent handled it, which tools ran, tokens/cost, business outcome | HTTP requests, exceptions, dependency latency, distributed traces |
| Backed by | `observability_runs` Cosmos container (or in-memory locally) — see ADR-0012 | Application Insights — **provisioned in Bicep, not instrumented in code** (see §11) |
| Never persists | Chain-of-thought / hidden reasoning (CLAUDE.md §10) | — |

## 3. Architecture

```
POST /chat (apps/api/src/api/routes/chat.py)
  -> AgentRequest{message_id, correlation_id}  (PBI-13-01: correlation_id is now actually
     threaded through — previously generated by CorrelationIdMiddleware but never passed on)
  -> SupervisorOrchestrator.handle(request, on_react_event=collector)
       -> Agent.handle(request, context, on_react_event)
            -> ToolCallingOrchestrator.run(..., on_event=on_react_event)   # ReAct loop,
               unchanged — only an optional, best-effort event hook added (ADR-0011 still
               governs the loop itself; this PBI instruments it, does not replace it)
  -> ObservabilityService.record_run(...)   # best-effort, never raises, never blocks the
     chat response (PBI-13-01 §3) — builds a RunRecord from AgentResponse + collected
     ReActEvents and persists it via ObservabilityRepository

GET /observability/summary | /conversations | /conversations/{id} | /runs/{id}
  -> api.observability_access.require_observability_access (centralized authorization, §8)
  -> ObservabilityService (read paths) -> ObservabilityRepository
```

`ObservabilityService` (`src/observability/service.py`) is the single shared abstraction
PBI-13-01 §3 requires — instrumented at the API-layer boundary (after
`SupervisorOrchestrator.handle()` returns/raises), not scattered as ad hoc Cosmos writes inside
every agent.

## 4. Correlation model

| Identifier | Source | Notes |
|---|---|---|
| `conversation_id` | Existing (`src.domain.conversation.Conversation.id`) | Unchanged. |
| `message_id` | New — generated in `chat.py`, threaded through `AgentRequest.message_id` | Becomes the persisted **assistant** `Message.id` (`SupervisorOrchestrator._persist_turn`), so a run and the message it produced share an id. |
| `run_id` | New — generated in `chat.py`, one per `POST /chat` call | Observability-only; never persisted to the conversation store. |
| `trace_id` | Alias of the existing `correlation_id` (`X-Correlation-ID` header / `CorrelationIdMiddleware`) | **Not** a real OpenTelemetry trace id — none exists in this codebase (see §11). Documented honestly as an alias, never fabricated as a distinct identifier. |
| `user_id` | `AuthenticatedUser.user_id` (`{tid}:{oid}`), from the validated Entra ID token only | Never a client-supplied value, at any layer — see `apps/api/src/api/auth/validator.py`. |

## 5. Data model

See `src/domain/observability.py` for the authoritative Pydantic schema (`RunRecord`,
`RunToolCall`, `RunTokenUsage`, `ConversationSummary`, `SummaryKpis`). Every field that cannot
be reliably populated today is `None`/"Unavailable" — never a fabricated value (PBI-13-01 §7).

Persistence design and its rationale: **ADR-0012**.

## 6. ReAct/Tool-Calling instrumentation

`ToolCallingOrchestrator.run()` (`src/core/tool_calling/orchestrator.py`) gained one new,
optional, default-`None` parameter: `on_event: ReActEventSink | None`. When provided, it is
called (synchronously, exceptions swallowed — a raising observer can never break the loop) at:
`reasoning_iteration_started`, `tool_required`, `tool_selected`, `tool_executed` (with
success/latency), `final_answer_reached`, `stopped_max_iterations`, `stopped_timeout`.
`ReActEvent` (`src/core/tool_calling/models.py`) has no field capable of holding free-text
reasoning — structurally, not just by convention (see
`tests/unit/core/tool_calling/test_react_events.py`).

Token usage/model name were previously captured by `AzureOpenAIProvider` but dropped before
reaching the orchestrator. `ToolCallingResponse` now accumulates `usage`/`model` across every
LLM call in one `run()` invocation; `AgentResponse` carries them through to the API layer. This
covers the ReAct loop's own LLM calls — an agent's separate prompt-diagnostics annotation call
(where present) is intentionally **not** included; the metric is labeled accordingly.

## 7. Cost calculation

`src/observability/pricing.py`: `estimated_cost_usd = input_tokens/1e6 * input_price +
output_tokens/1e6 * output_price` (direct model cost only — never Container Apps/Cosmos/App
Insights/networking/AI Search allocation, PBI-13-01 §15). Prices come from a versioned JSON
catalog (`configs/observability/pricing.json`, path configurable via
`OBSERVABILITY_PRICE_CATALOG_PATH`), never hardcoded in Python or React. **The shipped catalog
is empty** — this repository has no verified, current Azure OpenAI price list; cost figures
show "Unavailable" until a real, dated price entry is added. Schema:

```json
{
  "catalogVersion": "2026-08-12.1",
  "entries": [
    {
      "model": "gpt-5-mini",
      "effectiveDate": "2026-08-12",
      "inputPricePerMillionTokensUsd": 0.25,
      "outputPricePerMillionTokensUsd": 2.00
    }
  ]
}
```
Every `RunRecord` persists the `pricing_snapshot_version` (the catalog's own `catalogVersion`)
used for its cost estimate.

## 8. Access control

`OBSERVABILITY_ACCESS_MODE=all_authenticated` (V1 default): **every** authenticated user may
see **every** conversation's observability data — a deliberate V1 design choice (PBI-13-01
§16), not scoped per-user like the main chat's own `/conversations`. `OBSERVABILITY_ACCESS_MODE
=roles` is prepared (backend enforces it, `AuthenticatedUser.roles` parses the token's `roles`
claim if present) but **not activated**: no Entra App Role is created or assigned by this
codebase. See §13 for the exact activation steps. Enforcement:
`apps/api/src/api/observability_access.require_observability_access` — a FastAPI dependency
every observability route uses; returns HTTP 403 in `roles` mode without an allowed role,
regardless of frontend nav visibility (a direct URL/API call cannot bypass it).

## 9. Privacy and security

- Never exposes tokens/secrets/connection strings/system prompts/chain-of-thought — structurally
  absent from every observability model (no such field exists to populate).
- PII masking (`src/observability/masking.py`, `OBSERVABILITY_PII_MASKING=true` default):
  server-side regex masking of email/phone/synthetic-policy-number patterns, applied before
  `ConversationSummaryResponse.last_message_preview` / `ConversationMessageResponse.content`
  ever leave the API.
- Retention: `OBSERVABILITY_DETAIL_TTL_DAYS` (default `-1`, no expiry) maps to the Cosmos
  container's TTL, same convention as the existing conversation store.

## 10. Environment variables

| Variable | Default | Purpose |
|---|---|---|
| `OBSERVABILITY_ENABLED` | `true` | Registers/unregisters the `/observability/*` router entirely (404 vs. present). |
| `OBSERVABILITY_ACCESS_MODE` | `all_authenticated` | `all_authenticated` \| `roles` (prepared, not activated). |
| `OBSERVABILITY_ALLOWED_ROLES` | `Observability.Admin,Observability.Support,Observability.Auditor` | Comma-separated; only read when `OBSERVABILITY_ACCESS_MODE=roles`. |
| `OBSERVABILITY_STORE_PROVIDER` | `in_memory` | `in_memory` \| `cosmos`. |
| `COSMOS_DB_ENDPOINT` / `COSMOS_DB_DATABASE` | — / `tmxap-conversation-db` | Reused from the existing conversation store settings when `OBSERVABILITY_STORE_PROVIDER=cosmos`. |
| `OBSERVABILITY_RUNS_CONTAINER` | `observability_runs` | The dedicated Cosmos container (ADR-0012). |
| `OBSERVABILITY_PII_MASKING` | `true` | Server-side masking toggle. |
| `OBSERVABILITY_PRICE_CATALOG_PATH` | `configs/observability/pricing.json` | Versioned price catalog location. |
| `OBSERVABILITY_DETAIL_TTL_DAYS` | `-1` | Retention for detailed run telemetry (Cosmos TTL). |
| `VITE_OBSERVABILITY_ENABLED` (frontend) | `true` | Client-side kill switch for the nav link/routes — real authorization is always server-side regardless. |

## 11. Application Insights / OpenTelemetry relationship

**Confirmed (repository inspection, PBI-13-01 §0):** Application Insights is provisioned by
`ops/bicep/modules/app-insights.bicep` and its connection string is injected as an env var into
both Container Apps — but **no Python code anywhere in this repository reads it, instruments
FastAPI, or exports spans/traces/metrics to it.** No `opentelemetry-*` package is declared in
either `pyproject.toml`. This is a pre-existing gap, not something this PBI introduces or
silently papers over. Standing up real OpenTelemetry/Application Insights instrumentation is a
materially separate undertaking (SDK integration, exporter configuration, sampling strategy)
and is explicitly **not** part of this PBI (PBI-13-01 §18 tells us to "implement only what is
justified by the current architecture"). Until that future PBI, `trace_id` in this data model is
an honest alias of the existing `correlation_id` (§4) — never a fabricated OTEL id.

## 12. Delivery status

**Phase 1 (this PBI): delivered.** Correlation IDs, `ObservabilityService`/repository
abstraction, run persistence, conversation aggregates, `all_authenticated` authorization,
summary/conversation-list/conversation-detail/run-detail APIs, `/observability` dashboard +
detail page, chat integration instrumentation.

**Phase 2 (deferred):** data completeness / repeated-question / intent-change / duplicate-tool
/ missing-critical-field / goal-completion signals, and the Operational Quality Score
(configurable weights: intent confidence 30%, data completeness 25%, tool execution 30%,
grounding 15%; safety caps: required-policy-not-found → max 40%, critical-tool-failure → max
50%). `RunRecord`/`ConversationSummary` already reserve the fields
(`operational_quality_score`, `business_outcome`) this will populate — Phase 1 leaves them
`None`.

**Phase 3 (deferred):** advanced filters (quality/confidence range, cost range, error filter),
richer timeline, privacy/audit UX polish.

## 13. Activating Entra App Roles (future step)

This codebase never creates or assigns Entra App Roles. To activate `OBSERVABILITY_ACCESS_MODE=
roles` for real:

1. In the Entra App Registration (the one `entra_client_id` in
   `apps/api/src/config/settings.py` refers to), add three App Roles under "App roles":
   `Observability.Admin`, `Observability.Support`, `Observability.Auditor` (value = display
   name, allowed member types = Users/Groups).
2. Assign specific users/groups to those roles under Entra ID → Enterprise applications → this
   app → "Users and groups".
3. Confirm a real token issued after assignment carries a `roles` claim with the assigned
   value(s) — `AuthenticatedUser.roles` (`apps/api/src/api/auth/validator.py`) already parses
   it; no code change is required.
4. Set `OBSERVABILITY_ACCESS_MODE=roles` (and, if the three default role names above were not
   used verbatim, `OBSERVABILITY_ALLOWED_ROLES`) in the API Container App's environment.
5. No frontend code change is required either — `Header`'s `showObservabilityNav` prop is
   already wired from a single boolean in `App.tsx`; a future PBI that wants the nav link
   itself to hide for a non-allowed role (not just the backend 403) would decode the token's
   `roles` claim client-side there.

## 14. Local execution

Backend: no extra setup — `OBSERVABILITY_STORE_PROVIDER` defaults to `in_memory`, same as the
conversation store. Frontend: `npm run dev` in `apps/web` — the Observability nav link appears
once signed in (`VITE_OBSERVABILITY_ENABLED` defaults to enabled). Dashboard data is real: send
a few chat messages first, then open `/observability`.
