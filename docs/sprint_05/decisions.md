# Sprint 05 Decisions and Deviations

Record sprint-specific decisions and deviations. Cross-sprint decisions belong in ADRs.

## 2026-08-08 — PBI-05-01: One `ClaimsAgent`, LOB-aware via data-driven field groups — no `AutoClaimsAgent`/`PropertyClaimsAgent`

**Decision:** `src/agents/claims/state.py`'s fixed module-level `FIELD_GROUPS`/`REQUIRED_FIELDS` constants were replaced with `_COMMON_FIELD_GROUPS`/`_LOB_FIELD_GROUPS` plus two functions, `field_groups_for(line_of_business)` and `required_fields_for(line_of_business)`. The single `ClaimsAgent`/`advance_claims_intake` workflow is unchanged in shape — it still dispatches on `ClaimsIntakeState.status` exactly as before — but now reads `state.line_of_business` (set from the authoritative `policy_lookup` Tool result, never guessed or LLM-inferred) to select which field groups apply. Auto adds vehicle/driver/drivability questions; Property adds affected-area/contents/habitability questions; both share date/time, location, loss type, injuries, third parties, contact phone.

**Deviation/status change:** None — directly implements requirement 9's explicit instruction not to create separate per-line-of-business Agents. This is the same "function over fixed constant" pattern already used elsewhere in the codebase (e.g., Broker's `REQUIRED_FIELDS_BY_INQUIRY` dict keyed by inquiry type) extended to a second axis (line of business) without introducing a new abstraction layer.

**How to apply:** A third line of business (e.g., "liability") would add one more entry to `_LOB_FIELD_GROUPS` and extend `_LINE_OF_BUSINESS_SYNONYMS` in `extraction.py` — no new Agent, no new state machine.

## 2026-08-08 — PBI-05-01: Small, bounded shared NLU helpers (`src/agents/shared/nlu.py`) — not a general-purpose NLP library, and never LLM-based

**Decision:** `resolve_relative_date`, `resolve_commission_period`, `strip_natural_prefix`, `detect_negated_topic` are plain regex/keyword functions, each with a narrow, single responsibility, reused by Claims/Broker/Commercial extraction modules instead of being duplicated three times. `MockLLMProvider` cannot perform real entity extraction (it is content-agnostic — confirmed by re-reading its implementation before designing this), so "understand ayer/anoche/la Hilux/el segundo trimestre" had to be deterministic regardless of provider, consistent with architecture principle #2 ("the LLM is not the source of truth").

**Deviation/status change:** None — a direct implementation of requirements 3, 4, 7 (natural entity extraction), scoped to exactly the phrase patterns those requirements' own worked examples need, not a speculative general date/NLP parser.

**How to apply:** Any new natural-language pattern needed by a future Agent (e.g., a new relative-date phrase) should be added to these shared functions, not re-implemented locally in that Agent's own `extraction.py` — the whole point of this module is to prevent the three-way duplication that existed before this PBI.

## 2026-08-08 — PBI-05-01: Conversational Policy is a deterministic template/vocabulary layer, not an LLM-authoring mechanism

**Decision:** `src/agents/shared/conversational_policy.py` (`loss_type_label`, `opening_acknowledgment`) generates plain-language acknowledgment strings ("Lamento lo ocurrido. Voy a ayudarte a registrar el aviso...") from a bilingual lookup table keyed by `loss_type`, exactly like every other message catalog in this codebase since PBI-04-04. The LLM/PromptManager wiring is untouched — still invoked every turn, still surfaced only as `metadata["diagnostics"]`, never as the visible response (PBI-04-04's own decision, preserved here).

**Deviation/status change:** None — extends the existing catalog-plus-grouping pattern (see `docs/sprint_04/decisions.md`'s "Natural conversation... via better deterministic templates" entry) to opening empathy, rather than revisiting the "response authorship" architecture question.

**How to apply:** A new loss type needs one new dict entry in `_LOSS_TYPE_LABELS`/`_ACKNOWLEDGMENTS` (both languages) — no code change.

## 2026-08-08 — PBI-05-01: `carry_forward_other_agent_state` — cross-domain handoffs no longer destroy the other domain's in-progress state

**Decision:** `AgentResponse.metadata` is fully replaced (not merged) by `ConversationRepository.append_message` on every turn — a documented characteristic since PBI-04-04. Before this PBI, a domain handoff (e.g., Claims → Broker) meant the Broker's own next `AgentResponse.metadata` dict never included `claimsIntakeState`, so it silently vanished from the stored conversation the moment Broker took its first turn — if the caller later returned to Claims mid-intake, all prior answers would be gone. Fixed with `src/agents/shared/state_persistence.py::carry_forward_other_agent_state(metadata, own_key)`, called at the top of `ClaimsAgent.handle()`/`BrokerAgent.handle()`/`CommercialIntakeAgent.handle()` and spread into every returned `metadata` dict (including exception/fallback paths).

**Deviation/status change:** None — a correctness fix required by requirement 5's "preserve domain-specific workflow state... must not incorrectly drive the other's behavior," found by design inspection (reading `append_message`'s replace-not-merge contract before building the handoff logic), not by live testing.

**How to apply:** Any future fourth Agent must add its own state key to `KNOWN_AGENT_STATE_KEYS` and follow the same two-line pattern (`other_agent_state = carry_forward_other_agent_state(...)` at the top of `handle()`, `**other_agent_state` spread into every returned metadata dict) — omitting it reintroduces silent cross-domain state loss.

## 2026-08-08 — PBI-05-01: Fixed a pre-existing, higher-severity bug found while building the handoff fix — `Conversation.current_agent` was never updated after the first turn

**Decision:** While implementing `carry_forward_other_agent_state` and writing its integration test, inspection of `_persist_turn` in `src/supervisor/orchestrator.py` showed `ConversationRepository.append_message` was never passed `current_agent` — so `Conversation.current_agent` stayed permanently fixed at whatever Agent handled the conversation's very first turn. The Supervisor's own "stay with the current agent on an ambiguous follow-up" fallback (existing since PBI-01-06) therefore always compared against the *first-turn* agent, not the *most-recently-handled* agent — meaning a Claims→Broker→Commercial conversation would incorrectly keep trying to route ambiguous follow-ups back to Claims no matter how many turns had passed. Fixed: `ConversationRepository.append_message` (Protocol, in-memory adapter, Cosmos adapter) gained an optional `current_agent: str | None = None` parameter; `_persist_turn` now passes `current_agent=response.agent` on every turn.

**Deviation/status change:** A genuine pre-existing defect (present since PBI-01-06, invisible to every prior single-agent-only conversational test), not introduced by this PBI — fixing it was necessary for requirement 5's "do not reroute short follow-ups via naive keyword matching back to Claims" to be correctly implementable at all.

**How to apply:** Any future code path that persists a turn outside `_persist_turn` must also pass `current_agent` — a repository that silently drops it would reintroduce exactly this bug. Regression coverage: `tests/unit/services/test_in_memory_conversation_repository.py` (2 new tests) and `tests/unit/supervisor/test_orchestrator.py::test_handle_updates_current_agent_on_every_turn_not_just_creation`.

## 2026-08-08 — PBI-05-01: Broker natural discovery defers resolution until both `broker_name` AND `commission_period` are known — Claims resolves eagerly after just the name; the difference is intentional, not an inconsistency

**Decision:** `ClaimsAgent` looks up the customer immediately after `customer_name` alone is captured, because it then needs to show a policy list for disambiguation ("la primera"/"la Hilux") — an unavoidable second round-trip regardless of when the period-equivalent field is known. `BrokerAgent`'s `_handle_looking_up_broker` deliberately waits until `broker_name` and `commission_period` are both known before calling `broker_lookup`, because commission lookups need both to produce a single, useful answer — resolving the broker alone first would just mean asking a second question anyway, with no disambiguation benefit Claims has. This mirrors Broker Services' own pre-existing "ask both together" combined-question pattern from PBI-04-04, applied to natural broker-name discovery.

**Deviation/status change:** None — discovered while writing `test_broker_name_alone_is_captured_but_not_yet_resolved` (originally written assuming eager resolution, then corrected to assert the actual, intentional behavior once the reasoning above was worked through).

**How to apply:** Any future Broker inquiry type needing disambiguation among multiple same-name brokers (not currently a synthetic-data scenario) would need to adopt Claims' eager-lookup pattern instead — not assumed to be needed today.

## 2026-08-08 — PBI-05-01: Expanded synthetic demo portfolio via new customer `CUS-SYN-0003` (Carlos Mendoza, lapsed Auto policy) — additive only, no existing record renamed or removed

**Decision:** `src/services/tools/synthetic/provider.py` gained one new customer/policy/payment/coverage record set (`SYN-POL-1004`, Honda CR-V 2019, `status="lapsed"`, `payment_current=False`) to cover the lapsed-policy demo scenario requirement 16 asked for, plus a new `property_description: str | None` field on `SyntheticPolicyRecord` (additive, defaults to `None`) so Property policies can carry a meaningful description symmetric to Auto's existing `vehicle_description`. A module docstring was added documenting the ID-namespace history (`POL-SYN-*`/`BRK-SYN-*` → `SYN-POL-000x` → `SYN-BRK-*` → `SYN-POL-1xxx`/`CUS-SYN-*`) so a future reader does not need to reconstruct it from git history.

**Deviation/status change:** None — the existing PBI-04-04 portfolio (Juan Pérez with two Auto policies, Ana Torres with one Property policy) already covered most of requirement 16's scenario list (multi-policy selection, active+current, active-with-Property); only the lapsed-policy and "policy retains last-known coverage" cases were missing, so exactly one new customer was added rather than rebuilding the portfolio. Target of "~6-10 demo scenarios, not hundreds" (requirement 16) is met: 3 customers, 4 canonical policies, spanning active/lapsed status, payment-current/not-current, Auto/Property lines, single/multi-policy.

**How to apply:** A lapsed policy retains its last-known coverage record on file (not an absent one) — `SYN-POL-1004`'s `SYNTHETIC_COVERAGES` entry is intentionally populated, matching how a real insurer's system would behave. Any future lapsed-scenario addition should follow the same pattern, not omit the coverage record.

## 2026-08-08 — PBI-05-01: Legacy `BRK-SYN-*`/`SYN-BRK-*`/`POL-SYN-*` ID namespaces left in place, not migrated — natural-language Tools search across all of them so the caller never needs to know which applies

**Decision:** Rather than renaming or removing any pre-existing synthetic ID namespace (which would break existing regression tests referencing those exact IDs by name, per requirement 17's own "do NOT break existing regression tests unnecessarily"), the new `BrokerLookupTool` and the existing `CustomerLookupTool`/`policy_lookup` all search across every namespace their respective record dict contains. A caller using natural language ("soy Synthetic Brokerage One") never sees or needs to know `BRK-SYN-001` vs `SYN-BRK-...` — resolution is by name, Tool-side, uniformly.

**Deviation/status change:** None — this is the minimum clean canonical mapping needed for coherent demo behavior requirement 17 asks for: a caller-facing behavior guarantee (never need to understand internal ID namespaces), not a data-migration project. No existing record was renamed.

**How to apply:** Any brand-new synthetic broker/policy record added in a future PBI should use the current canonical namespace (`SYN-POL-1xxx`/`CUS-SYN-*` for customer-linked policies) — legacy namespaces are frozen, not a template to keep extending.

## 2026-08-08 — PBI-05-01: Five bugs found via live DEV validation, each root-caused, fixed, regression-tested, and re-deployed before moving to the next scenario

**Decision:** Following this PBI's own mandated four-scenario live validation sequence (A: Auto claim, B: Property claim, C: Broker handoff, D: Commercial handoff), five genuine defects were found — none reported by the user, all self-discovered by actually driving real conversations against the deployed DEV API with rich, multi-fact Spanish messages (the same class of "only reachable via real multi-turn conversation" defect PBI-04-04 documented five of previously):

1. **Trailing punctuation broke policy selection.** `resolve_selection("La Hilux.", candidates)` failed because the word-set match compared `"hilux."` against `"hilux"`. Fixed: strip `" ,.;:!?"` from each word before the word-set intersection. Regression: `test_resolve_selection_tolerates_trailing_punctuation_on_the_selected_word`, `test_resolve_selection_ordinal_tolerates_trailing_punctuation`.
2. **`event_location` garbled by a flawed "strip known spans, use the remainder" heuristic.** A rich multi-clause message ("Ayer me chocaron por atrás en Reforma. Yo manejaba, no hubo lesionados...") produced `event_location = "Ayer me aron por atrás en Reforma. Yo manejaba, no hubo lesionados..."` — the mid-word span-stripping approach could not scale to richer messages. Replaced entirely with clause-based `_extract_location_phrase()`: split the message on `". "`, search each clause for an `"en <place>"`/`"at <place>"` marker, capture to the end of that clause. The whole `consumed_spans` mechanism was removed as dead code. Regression: `test_grouped_question_extracts_a_clean_location_from_a_rich_multi_clause_message`.
3. **Intent routing gap for Property losses that never say "siniestro"/"accidente."** The PBI's own canonical example, "Ayer llovió muy fuerte y se inundó mi casa.", fell through to `FallbackAgent`. Fixed: `_CLAIMS_KEYWORDS` extended with loss-type-describing words (inund/incendio/robaron/granizo/vandalismo/chocaron, flood/fire/hail/stolen/vandalism/collision). Regression: `tests/unit/supervisor/test_intent.py`, 4 new cases including this exact phrase.
4. **`matched_structured_field` over-gated the free-text fallback.** A rich Property message directly answering "¿Dónde ocurrió el incidente?" also mentioned "no hubo lesionados" — the injuries narrative-aside extraction incorrectly set `matched_structured_field = True`, gating off the location fallback entirely, so `event_location` silently stayed `None` and the question was re-asked. Fixed: removed `matched_structured_field = True` from the four narrative-aside extraction blocks (injuries, third parties, vehicle drivable, property habitable) — only "identifying token" extractions (policy number, date, email, phone, loss type) should gate the fallback, since narrative asides coexist with a direct answer rather than competing with it. Regression: `test_direct_answer_to_event_location_is_not_dropped_by_an_unrelated_fact_in_the_same_message`.
5. **The simple (non-grouped) free-text fallback had no location-phrase logic at all.** After fixing #4, a message directly answering the location question still captured the *entire raw message* as `event_location`, since only the grouped-question fallback path had clause-based extraction. Fixed: the simple fallback now calls `_extract_location_phrase()` when `last_asked_field == "event_location"`, falling back to the whole trimmed message only when no "en"/"at" marker is present (preserving correct behavior for bare answers like "In my driveway"). Regression: `test_direct_location_ask_extracts_a_clean_place_from_a_rich_multi_clause_reply`, `test_direct_location_ask_falls_back_to_the_whole_message_with_no_connector_word`.

**Deviation/status change:** None — all five are correctness fixes to functionality this same PBI introduced (richer multi-clause Spanish extraction), found through the PBI's own explicit live-validation requirement, exactly the same discovery pattern PBI-04-04 documented. Each was fixed, covered by a regression test, and the full backend suite + targeted redeploy of `ca-tmxap-dev-api` was re-run before the next scenario was attempted — never batched.

**How to apply:** This is the concrete, repeated argument (now true across two consecutive PBIs) for why live DEV validation against a real deployment is not optional for prompt/extraction/routing changes — `MockLLMProvider`-backed unit tests alone did not and structurally cannot catch any of these five defects, since all of them are deterministic-extraction bugs triggered only by realistically rich, multi-clause message shapes no existing unit test happened to construct. Any future extraction-logic change should budget for the same live-validation pass.

## 2026-08-08 — PBI-05-01: Frontend (`apps/web`) required zero changes

**Decision:** No file under `apps/web/` was modified this PBI. All requirements (Spanish-first conversation, natural extraction, empathy, LOB-aware Claims, natural broker/customer discovery, contextual handoff, friendly failures) are satisfied entirely by backend response content — the existing Web UI (PBI-04-02/04-04) already renders whatever Spanish text the backend sends, with no technical badges, exactly as before. Per this PBI's own Section 23, `ca-tmxap-dev-web` was therefore **not** rebuilt or redeployed — only `ca-tmxap-dev-api` was, across the five bug-fix cycles above.

**Deviation/status change:** None — a direct consequence of "deploy ONLY changed applications... web only if frontend changes are actually required."

**How to apply:** No frontend action needed for this PBI's changes to take effect; the already-deployed Web container continues to work unmodified against the updated API.
