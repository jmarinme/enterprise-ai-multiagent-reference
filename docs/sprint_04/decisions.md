## 2026-08-08 — PBI-04-01: Two real, pre-existing defects found and fixed in the inherited pipeline

**Decision:** Reading the existing `azure-pipelines.yml` before changing it (per this PBI's own explicit "Read first" instruction) surfaced two genuine bugs, neither introduced by this PBI:

1. **Wrong Docker build context for the API image.** `ContainerBuildValidation`'s original step ran `docker build -t "$(apiImageName):$(imageTag)" ./apps/api`. `apps/api/Dockerfile`'s own header comment has required the **repo root** as the build context since PBI-03-02, because `main.py` depends on the shared, reusable `src/` packages (`src.supervisor`, `src.agents`, `src.domain`, `src.services`) which Docker cannot `COPY` from outside the build context — a single-directory context can never reach both trees. This command would have failed at the first `COPY src ./src` instruction had it ever actually been run with a real registry push attached (Sprint 0's version never pushed anywhere, so the bug was silent — the stage only proved a *local, throwaway* image tag could be *attempted*, and apparently was never actually exercised end-to-end against the post-PBI-03-02 Dockerfile). Fixed: `docker build --file apps/api/Dockerfile .` (repo root context), matching `docker-compose.yml`'s own `context: .` / `dockerfile: apps/api/Dockerfile` pattern and every `az acr build` invocation from PBI-03-05/06's real deployment validation.
2. **Stale Bicep module validation list.** `InfrastructureValidation`'s `bicepModuleFiles` parameter listed only 10 of the 14 files under `ops/bicep/modules/` — `ai-search.bicep` (PBI-02-02), `azure-openai.bicep` (PBI-03-02), and `private-dns-zone.bicep`/`private-endpoint.bicep`/`virtual-network.bicep` (PBI-03-04) were added by later PBIs but never added to this list, meaning the pipeline never actually validated them. Fixed: the list now matches `ls ops/bicep/modules/*.bicep` exactly (verified), 14 modules + `main.bicep`.

**Deviation/status change:** Both are corrections of latent, previously-undetected defects — not scope creep. Fixing them was necessary for this PBI's own stated objective ("Automatic Docker build" and "Automatic push to existing ACR" cannot work at all with the first bug present) and for "no regression" (the second bug meant Sprint-0's own stated CI coverage was silently incomplete).

**How to apply:** Any future new Bicep module must be added to this same `bicepModuleFiles` list as part of the PBI that adds it — this was the exact gap that let the list go stale for three PBIs running. Consider this list a checklist to update whenever `ops/bicep/modules/` gains a new file.

## 2026-08-08 — PBI-04-01: Container Build and Push Images combined into one YAML stage, not two

**Decision:** The user's own instructions list "Stage 4 — Container Build" and "Stage 5 — Push Images" as distinct numbered items. `azure-pipelines.yml` implements both inside a single YAML `stage: ContainerBuildAndPush`, as two separate, clearly-labeled `docker build`/`docker push` command groups within one job, rather than as two separate top-level `stage:` blocks.

**Deviation/status change:** A deliberate technical choice, not a shortcut: Azure Pipelines stages do not share a filesystem or Docker image cache across stage boundaries (each stage can run on a different agent instance) — a genuinely separate "Push Images" stage would need to `docker save` the just-built image, publish it as a multi-hundred-MB pipeline artifact, download it in the next stage, and `docker load` it, purely to satisfy a stage-per-numbered-item mapping. For a DEV-only pipeline with no manual approval gate between build and push (nothing would ever pause a real deployment *between* these two steps), that round-trip adds pipeline minutes and complexity with zero corresponding benefit — a violation of CLAUDE.md §7's "avoid unnecessary complexity." The two responsibilities remain fully visible and independently reviewable as separate `docker build`/`docker push` commands with their own `echo` markers in the step's inline script and this stage's own header comment.

**How to apply:** If a future PBI adds a manual approval gate or a security/vulnerability scan that must run *between* build and push (a real reason to need the artifact roundtrip), split them into two stages at that point — not before, since no such requirement exists today.

## 2026-08-08 — PBI-04-01: Image tag versioning (`dev-$(Build.BuildId)`) structurally avoids a bug discovered during PBI-03-05/06's manual validation

**Decision:** Every pipeline run tags both images `dev-$(Build.BuildId)` — Azure DevOps's own unique, monotonically increasing build identifier, prefixed for readability. Never `latest`, and never a fixed placeholder tag reused across runs.

**Deviation/status change:** None — directly required by this PBI's own "Use image versioning instead of latest whenever possible" instruction. Documented here because it also happens to structurally prevent a real bug PBI-03-05/06 hit manually: `az containerapp update --image <same-string-as-before>` is a no-op in Azure Container Apps (the platform compares the image string, not the resolved digest) — PBI-03-05/06 discovered this when reusing the placeholder tag `pending-first-build` across multiple manual redeploys and had to add `--revision-suffix` to force a new revision each time. Because every pipeline run's tag is genuinely unique, `az containerapp update --image ...` in `DeployDev` will always see a changed image string and always create a new revision correctly — no `--revision-suffix` workaround is needed or used.

**How to apply:** Do not introduce a shared/reused tag (e.g., `dev-latest`) into the routine pipeline flow — it would silently reintroduce the exact no-op-update bug this design already avoids.

## 2026-08-08 — PBI-04-02: Critical, pre-existing `ToolCallingOrchestrator` defect discovered during live validation — NOT fixed, out of this PBI's authorized scope

**Decision:** Live multi-turn validation against the real Azure OpenAI (`gpt-5-mini`) deployment surfaced a genuine, previously-undetected defect: `src/core/tool_calling/orchestrator.py::run()` (lines ~113-122), after executing an LLM-requested tool call, appends only a `role="tool"` `LLMMessage` to the conversation before looping back for a follow-up LLM call — it never appends the preceding `role="assistant"` message containing the `tool_calls` request itself. The real Azure OpenAI API rejects this exact malformed sequence: `"Invalid parameter: messages with role 'tool' must be a response to a preceding message with 'tool_calls'."` (HTTP 400, surfaced to the client as a `500 Internal Server Error` via the existing `LLMProviderError` path). `MockLLMProvider` — the only provider every existing automated test exercises this loop against — never validates OpenAI's real message-sequencing constraint, so this defect was invisible through PBI-01 through PBI-03-06's entire test suite and every prior manual smoke test (none of which happened to need a *second* LLM round-trip after a tool call against the real API).

**Scope of impact, precisely determined via live testing, not assumed:** Only `ClaimsAgent` is wired to `ToolCallingOrchestrator` (confirmed in `apps/api/src/api/dependencies.py`'s `get_supervisor()` — `BrokerAgent`/`CommercialIntakeAgent` receive no `tool_calling_orchestrator` argument at all). `BrokerAgent` and `CommercialIntakeAgent` invoke Tools through a separate, deterministic path (not LLM-driven function-calling), confirmed unaffected by live multi-turn tests (both completed a full 2-turn exchange, including real Tool-sourced business data, with `200` responses). `ClaimsAgent`'s first turn (routing + LLM response + RAG grounding + citations, no tool call yet) also succeeds live. The defect fires specifically the moment the LLM decides to request *any* tool call within a Claims conversation and the orchestrator loops back for the tool result to be incorporated — which is expected to happen in essentially every realistic, complete Claims intake conversation (policy validation, claim registration), making full multi-turn Claims currently broken against the real Azure OpenAI deployment.

**Deviation/status change:** Discovered, not caused, by this PBI — no source change in `src/agents/`, `src/core/tool_calling/`, or `src/llm/` was made this PBI (confirmed by `git status`/`git diff`: only `apps/api/src/{main.py,config/settings.py}`, `apps/web/**`, `ops/bicep/main.bicep`'s `CORS_ALLOWED_ORIGINS` line, and this documentation were touched). Per this PBI's own explicit instruction ("Do not modify Agents, Supervisor, Tools, RAG, PromptManager, LLMProvider, Cosmos, or Azure infrastructure"), `orchestrator.py` was correctly left unmodified even though the fix is well-understood and precise (insert an `assistant` `LLMMessage` carrying the model's own `tool_calls` before the `tool`-role result message(s), mirroring the OpenAI/Azure OpenAI chat-completions contract exactly).

**How to apply:** This is an urgent, precisely-scoped, high-value follow-up PBI — fix `ToolCallingOrchestrator.run()` to append the assistant's own tool-calling message to `conversation` before the tool result message(s), add a unit test asserting the resulting message sequence is well-formed (assistant-with-tool_calls immediately followed by matching tool-role messages), and re-validate a full multi-turn Claims conversation against the real Azure OpenAI deployment end-to-end. Until fixed, this PBI's live validation documents Claims as working end-to-end for a single turn only (including real grounded RAG citations) — see `validation.md` for the exact evidence and the honest STOP CONDITION accounting.

## 2026-08-08 — PBI-04-03: `ToolCallingOrchestrator` fixed to be Azure OpenAI protocol-compliant — the exact follow-up the PBI-04-02 entry above called for

**Decision:** `src/llm/models.py`'s `LLMMessage` gained a new field, `tool_calls: list[ToolCallRequest] | None = None`, set only on an `ASSISTANT`-role message representing the model's own prior request to invoke one or more Tools — the missing piece of typed vocabulary that made a protocol-compliant assistant message unconstructable before this PBI. (`ToolCallArgument`/`ToolCallRequest` were moved earlier in the file, before `LLMMessage`, so the new field could reference `ToolCallRequest` directly rather than via a forward-reference string — a pure reordering, no behavior change.) `src/core/tool_calling/orchestrator.py::run()` now appends exactly one `ASSISTANT` message carrying `llm_response.tool_calls` (and any accompanying text) to `conversation` *before* the loop that appends the `TOOL` result message(s) — provider-agnostic, no special-casing, no new parameter, no new class. `src/llm/azure_openai_provider.py::_to_openai_messages` gained a branch mapping an `ASSISTANT` message with `tool_calls` to the OpenAI SDK's `ChatCompletionAssistantMessageParam` shape (`role="assistant"`, `content` or `None`, `tool_calls=[{id, type:"function", function:{name, arguments}}]`) via a new `_to_openai_tool_calls` helper — the exact inverse of the existing `_from_openai_tool_calls`. `src/llm/ollama_provider.py::_to_ollama_messages` received the equivalent, Ollama-shaped branch (no `id`, arguments as a plain object) for full consistency across every provider that must now correctly forward the richer shared contract — not fixing Ollama too would have left a latent, provider-specific gap even though Ollama's own API may tolerate it more loosely than Azure OpenAI does. `src/llm/mock_provider.py` required **zero changes** — its tool-call-detection logic (`_should_request_tool_calls`) only ever inspects `TOOL`-role messages, which are unaffected by this fix.

**Deviation/status change:** None — this is precisely the fix the PBI-04-02 decision entry above already diagnosed and prescribed, implemented exactly as anticipated, in the minimum set of files (`src/llm/models.py`, `src/core/tool_calling/orchestrator.py`, `src/llm/azure_openai_provider.py`, `src/llm/ollama_provider.py`, plus their test files) with zero changes to `src/agents/`, `src/supervisor/`, `configs/prompts/`, `src/rag/`, `src/tools/`, or any frontend code (confirmed via `git status`).

**Validated live, not merely by unit test:** After rebuilding and redeploying only `ca-tmxap-dev-api` (a new versioned image tag, `az containerapp update --image`, no `az deployment group create`, no other resource touched), the exact 2-turn Claims sequence that previously failed with `500` (`"I want to report an accident."` → `"SYN-POL-0001"`) now returns `200`, with a real `policy_lookup` Tool call executed successfully (`"toolCalls":[{"toolName":"policy_lookup","success":true,"data":{...}}]`). The conversation was then driven a full **10 turns** to completion against the real `gpt-5-mini` deployment, ending in a genuine `claim_reference: "SYN-CLM-2026-0001"` and `adjuster_assigned: "Synthetic Adjuster Chen"` — the complete Claims intake workflow, including multiple real Tool calls across the conversation, working end-to-end for the first time against the real Azure OpenAI provider. Broker and Commercial were independently re-verified live (2-turn conversations each, real Tool-sourced business data returned) to confirm zero regression, exactly matching their pre-fix behavior since neither ever used `ToolCallingOrchestrator`.

**How to apply:** Any future new `LLMProvider` implementation must map an `ASSISTANT` message with `tool_calls` set to whatever shape that provider's own chat-completions-style API expects an assistant tool-call request to take — `AzureOpenAIProvider`'s and `OllamaLLMProvider`'s own mapping functions are the reference implementations to follow. `MockLLMProvider` deliberately needs no equivalent mapping (it never serializes `LLMMessage` to an external wire format), which is precisely why this class of protocol defect can only ever be caught by testing against a real provider — a standing reminder for any future Tool-Calling-adjacent change to re-validate live, not stop at the (necessarily incomplete) mock-backed test suite.

## 2026-08-08 — PBI-04-04: Language is resolved once per conversation, deterministically, and stuck via metadata — never LLM-detected, never re-detected mid-conversation

**Decision:** New `src/agents/shared/language.py`: `Language = Literal["es-MX", "en"]`, `DEFAULT_LANGUAGE = "es-MX"`. `detect_language(message)` is a small, deterministic heuristic (Spanish diacritics/ñ/¿/¡ → es-MX immediately; otherwise a bilingual keyword-signal count, English winning only if it strictly outnumbers Spanish signals; every tie or ambiguous message defaults to es-MX). `resolve_language(context_metadata, message)` returns the conversation's already-stored `metadata["language"]` if present (sticky), else a fresh `detect_language` call. Every multi-turn Agent (`ClaimsAgent`/`BrokerAgent`/`CommercialIntakeAgent`/`FallbackAgent`) calls `resolve_language` at the top of `handle()` and echoes the result back into its own `AgentResponse.metadata["language"]` every single turn — required because `ConversationRepository.append_message`'s own contract **replaces**, never merges, stored metadata (confirmed by reading its docstring before designing this), so a value not re-sent every turn would silently vanish on the next turn.

**Deviation/status change:** None — directly implements requirement 1 ("if the conversation starts in Spanish, continue in Spanish... keep English compatibility") and requirement 2 (Spanish routing). A real LLM-based language detector was deliberately rejected: `MockLLMProvider` is content-agnostic (CLAUDE.md's own architecture principle #2, "the LLM is not the source of truth," applies here exactly as it does to every other business fact) and a business-facing decision like "which language do I answer in" must be deterministic and testable, not a probabilistic LLM call that could flip mid-conversation.

**How to apply:** Any new multi-turn Agent must follow the same two-line pattern (`language = resolve_language(context.metadata, request.message)` at the top of `handle()`; include `LANGUAGE_METADATA_KEY: language` in the returned `AgentResponse.metadata`) — omitting the second line is the one way to reintroduce silent language amnesia after turn 1.

## 2026-08-08 — PBI-04-04: Bilingual message catalogs colocated per agent, not a shared i18n framework or library

**Decision:** Each agent's own `state.py`/`workflow.py` owns a `dict[str, dict[Language, str]]` catalog (`FIELD_PROMPTS`, `_MESSAGES`, etc.) resolved via a 15-line shared helper, `src.agents.shared.messages.t(catalog, key, language, **kwargs)` (es-MX fallback if a language entry is somehow missing). No `react-i18next`/`gettext`/`.po` files/translation-management service was introduced on either side. On the frontend, the handful of static English chrome strings (welcome message, button labels, placeholders, error text) were directly rewritten to Spanish in place — no i18n library was added to `apps/web/package.json` either.

**Deviation/status change:** A deliberate, scope-matched choice, not an oversight. This is CLAUDE.md §5's stack table taken literally ("Do not add... another [dependency]... unless the current PBI explicitly requires it") — the entire user-facing string surface (all 3 agents' notices/prompts plus the Web UI's static chrome) is small, finite, and fully known at build time; a translation-management framework earns its complexity at a scale (many languages, externally-editable translations, pluralization rules) this platform is nowhere near. Business logic determinism (CLAUDE.md §3) also argues against any framework that could inject "smart" runtime interpolation/pluralization behavior into what must remain a plain, auditable string lookup.

**How to apply:** If a third language is ever required, extend each catalog's `dict[Language, str]` value with the new language key and widen the `Language` literal in `src/agents/shared/language.py` — no other architectural change needed. If the string surface grows dramatically (e.g., full LLM-authored free text, which this PBI deliberately did NOT introduce — see the next entry — or externally-editable copy), revisit this decision with a real ADR at that point.

## 2026-08-08 — PBI-04-04: "Natural conversation" achieved via better deterministic templates and multi-field/grouped extraction — not by handing response authorship to the LLM

**Decision:** Every user-facing notice remains a deterministic, Tool-sourced string chosen from a bilingual catalog (as above) — never LLM-generated free text. "Natural conversation" (requirement 3) is delivered through three concrete, deterministic mechanisms already compatible with `MockLLMProvider`'s content-agnostic nature: (1) `src.agents.claims.extraction.extract_fields` already scanned one message for every matchable structured field in a single pass before this PBI (date/time/email/phone/loss_type) — confirmed by reading the pre-existing code before touching it, so "extract multiple facts from one message" required no new mechanism, just more fields to extract (customer name via the existing free-text-fallback mechanism); (2) new `FIELD_GROUPS`/`next_question_group()` in `src.agents.claims.state` batch related missing fields into one combined, hand-written question (e.g. date+location+loss-type asked together, injuries+third-parties asked together) instead of one field at a time — Broker Services already had exactly this pattern (`_COMBINED_COMMISSION_PROMPT`) for its own two-field commission lookup, extended here to Claims; (3) `missing_required_fields()` never re-asks an already-filled field, by construction (a plain `is None` check), so "never ask twice" is a structural property, not a runtime heuristic.

**Deviation/status change:** None — this preserves CLAUDE.md §3 ("Tool Calling for business action... every business query or action must use a deterministic, versioned, testable, and auditable Tool") and architecture principle #2 ("the LLM is not the source of truth") exactly as every prior sprint's Claims/Broker/Commercial Agents already did; PBI-04-04 extends the same pattern rather than replacing it. The `PromptManager`/`LLMProvider` invocation each agent still performs every turn (see the diagnostics entry below) remains a provable-wiring exercise, not the source of the visible response.

**How to apply:** Any future "make it feel more natural" request should extend this same catalog-plus-grouping pattern (new combined-question phrasings, broader keyword lists in `extraction.py`) rather than routing response authorship through the LLM — doing the latter would require re-litigating CLAUDE.md's core "AI First, not AI Only" principle via a real ADR, not a UX PBI.

## 2026-08-08 — PBI-04-04: Five real bugs found and fixed via live DEV validation, each with a regression test added afterward

**Decision:** Live, end-to-end validation against the real deployed DEV API (driving a complete Spanish claims conversation, not just unit tests against `MockLLMProvider`) surfaced five genuine defects that all 473 then-passing unit tests had missed — each fixed, covered by a new regression test, and re-validated live before moving on:

1. **Customer lookup deferred until the end of the conversation, not right after the name.** The original `_handle_collecting_information` treated `customer_name` as just another entry in the generic `FIELD_GROUPS`/`missing_required_fields()` loop, so `customer_lookup` only fired once every other incident-detail field (date, location, loss type, description, phone, injuries, third parties) was already collected — technically satisfying "search synthetic customer data" but at a confusing point in the conversation, and directly undermining requirement 4's intent (ask the name, then immediately show matching policies). Fixed: `customer_name` is now handled as its own priority step in `_handle_collecting_information`, checked and resolved (asked for, then looked up) before any `FIELD_GROUPS` question is ever reached. `state.py`'s `FIELD_GROUPS`/`REQUIRED_FIELDS` no longer include `customer_name` at all.
2. **Vehicle-description matching was backwards.** `resolve_selection`'s original vehicle-match check was `candidate.vehicle_description.lower() in lowered` — testing whether the *long* stored description ("toyota hilux 2021") appears inside the *short* caller reply ("la hilux"), which can never be true. Fixed to word-set intersection (`message_words & set(vehicle_description.lower().split())`), so "la Hilux" correctly matches the "Toyota Hilux 2021" candidate.
3. **A combined/grouped question silently dropped its free-text field.** Asking date+location+loss-type together only ever set `last_asked_field` to the first field (`event_date`); when the caller answered all three in one message, the pre-existing "free-text fallback" mechanism (keyed to a single `last_asked_field`) never captured `event_location`, since a structured match (the date) already fired and the fallback only applies when *nothing* structured matched. Fixed: new `ClaimsIntakeState.last_asked_group: list[str]`, set alongside `last_asked_field` whenever a grouped question is asked; `extract_fields` now separately recovers `event_location` from the message (stripping whatever structured spans — the date, a matched loss-type keyword — were already consumed, plus a leading "en"/"in"/"at" connector word) whenever `"event_location"` was part of the group just asked, independent of what `last_asked_field` itself matched.
4. **Declining the new confirmation step created a silent dead loop.** The first cut of `_handle_confirming`'s "no" branch reset only `confirmed`/`status`/`last_asked_field`, leaving every incident-detail field still filled — so the very next turn's `_handle_collecting_information` would find nothing missing and walk straight back to the identical `CONFIRMING` summary, with no way for the caller to actually change anything (traced through by hand before it ever reached DEV, not found live). Fixed: declining now also clears `event_date`/`event_time`/`event_location`/`loss_type`/`loss_description`/`contact_phone`/`injuries_reported`/`third_parties_involved` (never `customer_name`/`policy_number`/`holder_name`/coverage, already resolved), so the grouped re-ask flow genuinely re-collects the incident details.
5. **`GET /conversations`/`GET /conversations/{id}` only accepted `user_id`, not `userId`.** FastAPI's camelCase aliasing (`_CamelModel`'s `alias_generator=to_camel`) only applies to Pydantic request-body models — it does nothing for plain function-parameter query params, which is how `user_id: str` was originally declared on both routes. Every other caller on this API (the Web UI, `POST /chat`) uses `userId` on the wire; the routes silently only accepted the Python-side name, returning a 422. Fixed: `user_id: str = Query(alias="userId")` on both routes.

**Deviation/status change:** None of these are scope changes — all five are correctness fixes to functionality this same PBI introduced, found through the PBI's own explicit "perform live DEV validation" requirement. Each triggered a fresh full regression (`pytest`/`ruff`/`mypy`, then `vitest`/`tsc`/`eslint`/`build` where relevant) and a redeploy-then-revalidate cycle before moving to the next step — never batched into "fix everything, deploy once at the end" — consistent with CLAUDE.md §17's "relevant validations have run" and §7's "never claim success unless actually executed." New tests: `tests/unit/agents/claims/test_extraction.py` gained `test_grouped_question_recovers_event_location_alongside_a_structured_date`, `test_grouped_question_does_not_recover_event_location_when_not_part_of_the_group`, `test_resolve_selection_matches_a_spanish_ordinal_word`, `test_resolve_selection_matches_a_vehicle_description_word_in_a_short_reply`, `test_resolve_selection_returns_none_for_an_unrecognizable_reply`; new `tests/unit/api/test_conversations.py` (6 tests, including an explicit regression guard asserting `user_id=` as a raw query param is rejected with 422 while `userId=` succeeds).

**How to apply:** This is the concrete argument for why "run the full regression, deploy, then actually drive a real multi-turn conversation against the live deployment" is not optional busywork for a PBI like this one — none of these five defects were reachable by feeding `MockLLMProvider` isolated single-turn inputs the way most existing unit tests do; each only appeared once a real, multi-step, multi-field conversation was actually driven turn-by-turn. Any future PBI that adds a new grouped/combined question, a new confirmation-style gate, or a new query-parameter-based route should budget for the same live-validation pass, not just unit tests against the mock provider.

## 2026-08-08 — PBI-04-04: A known, accepted, smaller-scope limitation — a grouped yes/no question only captures one answer per message

**Decision:** The `injuries_reported`+`third_parties_involved` combined question ("¿Hubo personas lesionadas, y estuvieron involucrados terceros?") has the same class of "only one field captured per grouped message" gap as the event_location case above, but was deliberately **not** fixed the same way. Unlike the date/location/loss-type group (one structured field + one clearly-recoverable free-text remainder), a combined yes/no answer like "no hubo lesionados y sí, hubo un tercero" has no reliable deterministic way to split "which yes/no word belongs to which field" without much more elaborate parsing (positional heuristics break on word order like "sí, hubo terceros pero no lesionados"). When only one of the two answers is captured, the flow does not break or loop — it simply re-asks the second question individually on the next turn, which is honest and correct, just slightly less smooth than the date/location case.

**Deviation/status change:** Accepted, not fixed — a deliberate scope boundary discovered and documented during the same live-validation pass as the five bugs above, consistent with CLAUDE.md's "never claim... success unless actually executed": this PBI's STOP CONDITION claims "Claims works naturally," not "every combined question captures every answer in one message," and re-asking a single yes/no question is still natural, professional behavior, not a defect a caller would perceive as broken.

**How to apply:** If this specific gap is ever worth closing, the deterministic approach would be a small ordered-clause parser (split on "y"/"and"/","/";", match each clause's leading yes/no word to a field by position) scoped to exactly the `injuries_reported`/`third_parties_involved` pair — not a general-purpose combined-yes/no parser, which would be over-engineering for two fields.
