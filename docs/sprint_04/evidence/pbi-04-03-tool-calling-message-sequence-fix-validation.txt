=====================================================================
2. EXPLANATION (delivered before any code change, per explicit instruction)
=====================================================================

Current execution sequence: ToolCallingOrchestrator.run() sends [SYSTEM, USER] to the LLM. If
the LLM requests tool_calls, each is executed and only a role="tool" message is appended, then
the SAME conversation list is sent back to the LLM for a follow-up response.

Exact protocol violation: per OpenAI/Azure OpenAI's chat-completions contract, a role="tool"
message is only valid immediately following a role="assistant" message whose own tool_calls
field named that exact tool_call_id. The orchestrator never appended that assistant message.
Azure OpenAI validates this server-side and rejects it: "Invalid parameter: messages with role
'tool' must be a response to a preceding message with 'tool_calls'." (HTTP 400), surfaced to
the client as HTTP 500 via the existing LLMProviderError path.

Why MockLLMProvider never exposed it: MockLLMProvider.generate() is a pure Python function
that inspects the in-memory message list (count, last user message length) to compute a
deterministic string — it never serializes messages to any real API and has no concept of
"valid sequencing." Every automated test in this codebase (before this PBI) used
MockLLMProvider or an equally non-validating scripted double, so the malformed conversation
shape was structurally invisible until a real Azure OpenAI call happened during PBI-03-05/06's
live validation, and even then only manifests on the SECOND LLM round-trip within a
tool-calling turn (PBI-04-02's own live testing was the first time this exact path was
exercised for a genuine multi-turn conversation).

Minimum code change required:
  - src/llm/models.py: add tool_calls: list[ToolCallRequest] | None = None to LLMMessage.
  - src/core/tool_calling/orchestrator.py: append one ASSISTANT message carrying
    llm_response.tool_calls to `conversation` before the TOOL-message-appending loop.
  - src/llm/azure_openai_provider.py and src/llm/ollama_provider.py: extend each provider's
    own message-mapping function to correctly serialize the new assistant+tool_calls shape.
  - src/llm/mock_provider.py: no change needed.

3. IMPLEMENTATION
=====================================================================

src/llm/models.py:
  - Moved ToolCallArgument/ToolCallRequest class definitions before LLMMessage (pure
    reordering, no behavior change) so the new field could reference ToolCallRequest directly.
  - Added: tool_calls: list[ToolCallRequest] | None = None to LLMMessage, with a docstring
    explaining exactly why (root-cause reference).

src/core/tool_calling/orchestrator.py:
  - run(): immediately after "if not llm_response.tool_calls: return ...", before the
    "for call in llm_response.tool_calls:" loop, added:
      conversation.append(
          LLMMessage(
              role=LLMMessageRole.ASSISTANT,
              content=llm_response_text,
              tool_calls=llm_response.tool_calls,
          )
      )
    This is unconditional whenever tool_calls is non-empty, covering the success,
    unauthorized, unknown-tool, malformed-argument, and execution-failure cases identically,
    since all of them still produce a TOOL-role result message that now correctly has its
    preceding assistant message.

src/llm/azure_openai_provider.py:
  - New imports: ChatCompletionAssistantMessageParam, ChatCompletionMessageFunctionToolCallParam.
  - New _to_openai_tool_calls() helper — exact inverse of the existing _from_openai_tool_calls().
  - _to_openai_messages(): new branch for role==ASSISTANT and message.tool_calls truthy, mapping
    to {"role": "assistant", "content": message.content or None, "tool_calls": [...]}.

src/llm/ollama_provider.py:
  - _to_ollama_messages(): new branch for role==ASSISTANT and message.tool_calls truthy,
    mapping to Ollama's own documented shape (tool_calls: [{"function": {"name", "arguments"}}],
    no id, arguments as a plain dict — matching this file's existing, documented Ollama-specific
    conventions, not a new invention).

src/llm/mock_provider.py: unchanged.
