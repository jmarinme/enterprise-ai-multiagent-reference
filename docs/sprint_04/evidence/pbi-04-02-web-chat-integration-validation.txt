--- 6. Claims turn 2 (same conversationId, "SYN-POL-0001") ---
-> "Internal Server Error" (500)
Reproduced with a completely independent, fresh conversation (different userId,
conversationId be67d461-...) -> same result. Deterministic, not transient/flaky.

Root cause (read-only investigation, no source modified):
  az containerapp logs show --name ca-tmxap-dev-api --tail 40
  -> Traceback:
     File "/app/src/core/tool_calling/orchestrator.py", line 93, in run
       llm_response = await self._llm_provider.generate(...)
     File "/app/src/llm/azure_openai_provider.py", line 219, in generate
       raise LLMProviderError(_PROVIDER_NAME, str(exc)) from exc
     LLM provider 'azure_openai' failed: Error code: 400 - {'error': {'message':
     "Invalid parameter: messages with role 'tool' must be a response to a preceeding
     message with 'tool_calls'.", 'type': 'invalid_request_error',
     'param': 'messages.[2].role', 'code': None}}

  Read src/core/tool_calling/orchestrator.py (read-only): run()'s loop (lines ~113-122)
  appends only a role="tool" LLMMessage to `conversation` after executing a tool call — it
  never appends the preceding role="assistant" message carrying the model's own tool_calls
  request. On the next loop iteration's LLM call, the conversation sent to Azure OpenAI
  contains an orphaned "tool" message with no preceding "assistant...tool_calls" message,
  which the real API rejects outright. MockLLMProvider (the only provider every existing
  automated test exercises) never validates this OpenAI-specific sequencing constraint, so
  the defect was invisible through this entire project's test suite until this PBI's live,
  real-Azure-OpenAI multi-turn validation.

  Read src/agents/claims_agent.py (read-only): confirmed ClaimsAgent always sends only
  [SYSTEM, USER] as the initial messages list to ToolCallingOrchestrator.run() (no manual
  history reconstruction) — the bug is entirely internal to a single orchestrator.run()
  invocation's own loop, not a cross-turn Cosmos-history-reconstruction issue as initially
  hypothesized.

  Confirmed apps/api/src/api/dependencies.py: get_supervisor() passes
  tool_calling_orchestrator= only to ClaimsAgent — BrokerAgent/CommercialIntakeAgent receive
  no such argument, confirming they use a separate, deterministic Tool-invocation path, not
  LLM-driven function-calling.

NOT FIXED — src/core/tool_calling/ is explicitly forbidden for PBI-04-02
  ("Do not modify... Tools..."). Documented in full in docs/sprint_04/decisions.md as an
  urgent, precisely-scoped follow-up.
